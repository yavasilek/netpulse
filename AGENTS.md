# Инструкции проекта NetPulse для Codex

- Всегда отвечай пользователю на русском языке.
- Это нативное Android-приложение на Kotlin, Jetpack Compose и Gradle. Не добавляй веб- или Node-зависимости в runtime приложения; `package.json` используется только для Work Graph.
- Для локальной Android-сборки используй JBR из Android Studio: `JAVA_HOME=C:\Program Files\Android\Android Studio\jbr`.
- Перед завершением изменений запускай релевантные unit-тесты и lint. Для полной проверки используй `gradlew.bat testDebugUnitTest lintDebug assembleDebug`.
- Не изменяй ключи подписи, `local.properties`, секреты GitHub Actions и release-файлы без прямого запроса пользователя.
- Не публикуй APK, GitHub Release и Pull Request без отдельного разрешения.

## Work Graph

- Work Graph настроен только для этого репозитория как dev-инструмент и не входит в Android-приложение или APK.
- Локальный UI запускается командой `npm run workgraph:ui` на `http://localhost:4188/`.
- Проверка установки выполняется командой `npm run workgraph:doctor`.
- В Codex Local и Worktree runner-скрипты определяют текущий checkout самостоятельно; не закрепляй MCP за абсолютным `cwd` основного репозитория.
- Если в Codex worktree нет собственного `node_modules`, MCP и UI используют установленные devDependencies основного checkout. Для полностью зелёного `workgraph:doctor` и проектных npm-команд выполни `npm ci` в worktree.
- Для чтения и изменения work items используй MCP-сервер `workgraph`; не изменяй статусы, результаты проверок и служебные поля в `.work.bvc` напрямую.
- Автоматические git snapshots отключены. Не включай их и не вызывай `git_snapshot` без прямого запроса пользователя.
- Правила разработки остаются в `AGENTS.md`, а Work Graph используется для backlog, критериев готовности и результатов проверок.

### Автоматический цикл работы

- Пользователь ставит задачи Codex обычным текстом и не обязан управлять Work Graph вручную.
- Перед изменением кода, тестов, документации или конфигурации найди подходящий незакрытый work item и переиспользуй его без дубликата.
- Если подходящего work item нет, создай его через MCP с понятными `basis`, `vector`, `goal`, проверками, ожидаемыми файлами и ближайшим действием, затем возьми через `claim_work_item`.
- Во время выполнения поддерживай статус актуальным и добавляй через MCP результаты существенных проверок.
- Перед завершением вызови `assert_task_ready_for_done`, устрани найденные нарушения и закрой задачу через `complete_work_item`. Реальную блокировку зафиксируй с конкретной причиной.
- Простые ответы, чтение без изменений и сообщения о статусе не требуют нового work item, если пользователь явно не попросил их зафиксировать.
- Не проси пользователя вручную создавать, брать или закрывать задачи. Если MCP временно недоступен, продолжи безопасную работу и синхронизируй карточку после восстановления.
